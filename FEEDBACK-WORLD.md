## 1. How Sigil uses Selfie Check
Abuse prevention, load-bearing. Without a distinct-human proof, one operator opens a claim from wallet A, disputes it from wallet B with a trace they know fails, loses the bond back to themselves, and manufactures a "survived a dispute" record for the price of gas. Sigil stores the Selfie Check nullifier against every claim and every dispute and rejects a dispute whose nullifier matches the claim's (HTTP 409). The rule is enforced identically in mock mode, so the property is tested even before Sandbox access arrives.

Status: `WORLD_MODE=mock` in every run so far. The sandbox path (`POST /api/v4/verify/{rp_id}`, `rp_context` signing, `IDKitRequestWidget` in the web) is implemented and typechecks but has never received a real proof; the portal side (app, RP, registered signer, action) is done and `POST /world/rp-context` returns a signed context. The headless agent cannot run IDKit, so in sandbox mode it sends a bare `{ nullifier }`, which the gateway accepts only if the operator listed that nullifier in `WORLD_PREVERIFIED_NULLIFIERS` after verifying once through the web (item 21 in section 5). In mock mode the web derives the nullifier as `keccak256(stakerAddress)`, so the rule is visible in the browser: opening a claim and disputing it from the same address ends with `409: one personhood proof cannot hold both sides of a claim` in the form's step list.

Integration flow as built (`world.ts`, `HumanCheck.tsx`):

1. Web calls `POST /world/rp-context { action: "sigil-participant" }` on every click (a fresh context each time; see item 5 in section 5). Gateway calls `signRequest` and returns `{ rp_id, nonce, created_at, expires_at, signature }`.
2. Web mounts `<IDKitRequestWidget open onOpenChange app_id action rp_context allow_legacy_proofs={true} environment="sandbox" preset={selfieCheckLegacy({ signal: address })} onSuccess onError />`, loaded with `next/dynamic({ ssr: false })` because `idkit-core` ships WASM and reads `window`. `signal` is the staker's or disputer's Arc address so a proof cannot be replayed for another wallet.
3. `onSuccess` hands the full `IDKitResult` to the gateway as `worldProof` in `POST /claims` or `POST /claims/:id/dispute`; `onError(code)` is shown inline as `IDKit: <code>`.
4. Gateway forwards it verbatim to `POST https://developer.world.org/api/v4/verify/{rp_id}`. Non-2xx → HTTP 400 with the API's `detail`. 2xx → nullifier taken from `responses[0].nullifier` of the result it just sent, lower-cased, stored as `humanProofRef`.
5. Dispute handler: `if (humanProofRef === claim.humanProofRef) → 409`.

Findings from building this, before Sandbox access:

- Items 1, 2, 5, 7 and 8 of `WORLD-NOTES.md` were written against a reference project because we did not find the pages above on the first pass. Reading them now closes four of the five: the verify endpoint, the success body, the `signing` re-export, the 0x prefix, and the error body are all documented. The `rp_context` object shape that IDKit expects (snake_case, which fields) is still not on the signatures page; it is only in the SDK types (`RpContext` in `@worldcoin/idkit-core@4.2.4` `dist/index.d.ts`, JSDoc "This should be generated and signed by your backend"). Our object matches it and is type-checked by `IDKitRequestWidget rp_context=` in the web app.
- The information exists but is spread over seven pages in four sections (`world-id/idkit`, `world-id/credentials`, `world-id/sandbox`, `api-reference`). Nothing links "I want Selfie Check" to "here is the verify call you make for it".
- The assurance statement on `credentials/11` changed our README. Sigil's both-sides rule is as strong as the credential; we now say so and name `proofOfHuman` (Orb) as the upgrade.
- On the client the typings were the documentation. Everything `HumanCheck.tsx` passes to `IDKitRequestWidget` came from `node_modules/@worldcoin/idkit/dist/index.d.ts`, not from a docs page: the required `allow_legacy_proofs` boolean, the `` `app_${string}` `` template type on `app_id`, the `preset` xor `constraints` union (spreading a config object from state is a type error unless it is declared as `IDKitRequestHookConfig` up front; the package README shows this, the typings do not say why), and the `Preview: Selfie Check is currently in preview. Contact us if you need it enabled.` sentence that lives only in the JSDoc of `SelfieCheckLegacyPreset`. Items 15 to 20 in section 5 are what that cost.

## 3. Developer Portal navigation and debugging

What the docs say the portal contains, and what we could or could not do:

| Portal task | Documented where | Our result |
|---|---|---|

Projects → **Create new app** asks for a name only and lands on **World ID Configuration** showing `App ID` and `RP ID` side by side: the RP is created with the app, one per app, which no docs page says (`idkit/signatures` reads as if an RP were a separate object you create). Our portal bookmark was `developer.worldcoin.org`; the verify reference lists that host as a *legacy* API server and `developer.world.org` as current. No page says the portal moved too; `curl -I https://developer.worldcoin.org` answers `308 Location: https://developer.world.org/`, so it did |
| Create an RP, get `rp_…` and the RP signing key | `idkit/signatures` says "your backend signs requests with a signing key"; where the key is generated in the portal is not on that page | Done. **Register relying party** opens **Configure signer key** with two paths: *Generate new key* ("We'll generate a secure key in your browser. You'll download the private key") or *Use Existing Key* ("Provide a secp256k1 public key you control (e.g. Ethereum address)"). | Enable Selfie Check (Beta) for the app | `idkit/credentials`: "Request access to enable Selfie Check (Beta) for your app" (mailto) | **[pending sandbox]** requested; after creating the app we looked on World ID Configuration, the action page and the Verification wizard: there is no toggle, no status indicator and no expected turnaround anywhere in the portal |
| Request Sandbox tester access | `sandbox/sandbox-access`: sidebar **World ID Sandbox**, iOS / Android tabs | Reached. The sidebar card **World ID Sandbox / Install the test build** opens a dialog with iOS (TestFlight) and Android tabs, the account email pre-filled and a **Submit email** button, then three steps (install TestFlight, submit the Apple Account email, wait for the approval email). **[pending sandbox]** enrolment is per phone platform and approval is asynchronous; the portal shows no state after submitting |
| Configure an action (`sigil-participant`) | not found on any of the seven pages; we assumed the v3 "actions" model | Done. Dashboard (the actions tab) → **Create action** → identifier ("Lowercase letters, numbers, and dashes", 32 max) and a short description. The action page has only a *Verification history* panel ("No verifications yet") and *Delete*: there is no per-action *max verifications per user* setting any more and nothing about which credentials the action accepts, so whether the same human can verify twice for the same action (which Sigil needs: one human opens many claims) cannot be configured or even read in the portal. One action serves both claims and disputes so the nullifier is the same on both sides. Whether v4 uniqueness proofs are per-action or per-RP is not stated on the verify page |

Easy to miss, and nothing in the README says so. There is no code for "Selfie Check is not enabled for this app": the nearest are `feature_unavailable` and `credential_unavailable`, and which one an un-enabled app receives is not documented, so `onError` cannot tell "this user has no selfie credential" from "our app is not allowlisted" **[pending sandbox]** |

A naming trap: the sidebar item **Verification** is not credential configuration. It is a four-step app-listing wizard (logo, app URL, official website, Mini App vs External integration, availability, localised content, review). We opened it three times looking for Selfie Check settings.

Debugging aids we had to build ourselves, which the portal or SDK could provide:

- A mock mode. `WORLD_MODE=mock` accepts `{ mock: true, nullifier }` so the both-sides rule could be tested (`index.test.ts` section 4: same nullifier → 409, different → 201) with no device; the web's mock button derives a stable nullifier from the connected address so the same test runs in the browser. A documented "test nullifier" or a sandbox verify response that echoes a stable fake nullifier would have removed this code on both sides.
- An explicit "not configured" error instead of a crash when `WORLD_RP_SIGNING_KEY` is empty; the web shows that `500` verbatim under the button, and greys the button out with `NEXT_PUBLIC_WORLD_APP_ID is empty` when the app id is missing.

## 4. Sandbox: app states, proof flows, test users, errors, edge cases
- Documented states we planned to test: Hot / Cold / Semi-cold (from `testing-selfie-check`).
- Cold, per the docs: "the full funnel, including install, account creation, date of birth, invite code (iOS), enrollment, and Selfie Check". Semi-cold: "reinstall and account recovery, then completes Selfie Check". Hot: face match directly, or enrollment first.
- Documented limitation we will try to hit: "On iOS, if the user taps 'Sign in' instead of 'Sign up' mid-flow, there's no path to add the invite code" and "Invite-code handling in the Cold flow differs by platform".
- Documented caveats: "Sandbox apps aren't publicly listed in the app stores" (`testing-selfie-check`); from `world-id/sandbox`, under "What Sandbox is not": "Not production. Accounts and proofs issued in Sandbox are for integration validation only — not load testing, security certification, or production sign-off.", and under "Why use Sandbox": "Resettable accounts. Delete an account and sign up again as often as you need."
- **[pending sandbox]** actual results per state, on which platform, invite-code handling, whether we hit the semi-cold iOS dead end.
- The IDKit result keys for `selfieCheckLegacy()` are typed in the SDK (`IDKitResultV3` in `@worldcoin/idkit-core@4.2.4` `dist/index.d.ts`: `protocol_version: "3.0"`, `nonce`, `action?`, `responses: ResponseItemV3[]` with `identifier`, `signal_hash?`, `proof`, `merkle_root`, `nullifier`, plus `environment`), which is where the gateway's `responses[0].nullifier` read comes from. **[pending sandbox]** runtime confirmation, and whether the nullifier is identical across two proofs for the same test user and action. The both-sides rule depends on this.
- **[pending sandbox]** whether a proof for action A verifies under action B (it must not).
- **[pending sandbox]** whether `require_user_presence` changes the result shape or only adds the liveness step.
- **[pending sandbox]** client side, from `packages/web/WORLD-NOTES.md`: the exact `IDKitResult` keys and `responses[0].identifier` for one real `selfieCheckLegacy` run; the error code when `allow_legacy_proofs: false` meets `selfieCheckLegacy`; the code an un-enabled app receives; whether `signal` must be pre-hashed with `hashSignal` for `/api/v4/verify` to accept it (`ResponseItemV3.signal_hash` suggests the hash comes back); whether the widget renders and closes cleanly under Next 16 / React 19 with `ssr: false`.
- **[pending sandbox]** the 90-day inactivity window cannot be tested in a hackathon; we will note whether the sandbox exposes a way to expire a credential.

## 5. What was confusing, missing, broken or hard to test

Each item: the sentence, what we expected, the fix we propose.

1. **"Once enabled, use `selfieCheckLegacy()`" with no "enabled where".** `idkit/credentials` says access is by email. Expected: a toggle in the portal under the app, with a status (requested / enabled). Fix: put the request form or toggle in the portal and link it from that sentence; state the expected turnaround.
2. **No lead-time statement anywhere in `sandbox-access`.** TestFlight and Play approvals are asynchronous and the portal shows nothing. Expected: "approval usually takes N business days; you will get an email". Fix: one sentence plus a status row in the World ID Sandbox screen.
3. **Version split with no single diagram.** `selfieCheckLegacy` "uses World ID 3.0; World ID 4.0 support is not yet available", the verify reference is v4-first with a v3 "legacy" body, `proofOfHuman` is 4.0 "with legacy Orb fallback". Expected: one table: preset → protocol version → verify body variant → nullifier field. Fix: add that table to `idkit/credentials`.
4. **Two hosts.** The verify reference lists `developer.world.org`, `developer.worldcoin.org` (legacy) and `staging-developer.worldcoin.org` as API servers. Our portal bookmark was `developer.worldcoin.org`; it 308-redirects to `developer.world.org` (`curl -I`), so the portal did move with the API, but no page we read says so. Expected: one host, or a sentence saying the portal and the API moved together. Fix: state on every page which host is current (the redirect is already in place).
5. **`rp_context` shape and lifetime are not documented next to `signRequest`.** `signRequest` returns camelCase `{ sig, nonce, createdAt, expiresAt }`; the object IDKit consumes is snake_case `{ rp_id, nonce, created_at, expires_at, signature }`, documented only in the SDK types (`RpContext` in `idkit-core` `dist/index.d.ts`), not on the signatures page. We got this wrong once. Our object matches and is type-checked by `IDKitRequestWidget`. `RpContext.expires_at` exists but nothing says how long a context should live, and the widget does not expose "expired, fetch a new one"; the only hint is the error code `rp_signature_expired`. Our UI fetches a fresh context on every click, which is safe but wasteful. Fix: have `signRequest` (or a sibling `rpContext()`) return the exact object IDKit wants, document the mapping and a recommended `ttl` on the signatures page.
6. **The verify success body is documented but the nullifier's provenance is unclear.** The response carries `nullifier`, and `results[]`. Our gateway reads `responses[0].nullifier` from the client payload it forwarded, because the reference did. Expected: a sentence "use `nullifier` from the response, not from the client payload" (it removes a trust-on-client step). Fix: say which field is authoritative for uniqueness and whether it is present for legacy v3 proofs.
7. **Nullifier stability for Selfie Check is not stated.** `credentials/11` says it "does not provide a strict one-person-one-account guarantee" and "returns a proof of the completed check, not a numeric Sybil or uniqueness score". For a both-sides rule we need: is the nullifier stable per (person, action) like an Orb v3 nullifier, or per proof? The typings have two shapes, `ResponseItemV3.nullifier` (legacy, what Selfie Check returns) and `ResponseItemV4.nullifier` ("RP-scoped"), plus `ResponseItemSession.session_nullifier` as a string array, and none of the three says whether it is stable. If the V3 one rotates, our rule degrades to per-proof. Expected: an explicit "nullifier semantics" line on every credential page and on each `ResponseItem*` type. Fix: add it; if Selfie Check nullifiers are per-session, say that relying parties needing uniqueness must use `proofOfHuman`.
8. **Is `environment: sandbox` server-side or client-side?** `sandbox-access` says set it in IDKit and verify at the same production URL; the verify response has an `environment` field. We guessed: client flag, same endpoint, response tells you which. On the request config `environment` is typed as the literal `"sandbox"`, on `IDKitResult` it is a plain `string`, so a gateway that wants to refuse production proofs in sandbox mode (or the reverse) has nothing to compare against except a magic string. Expected: one sentence saying exactly that, and a string-literal union on the result. Fix: add both.
9. **Which package owns `signRequest`.** `@worldcoin/idkit-server` exports it; `@worldcoin/idkit-core/signing` and `@worldcoin/idkit/signing` re-export it. We installed `idkit-core` in the gateway and it works, but the docs example imports `idkit-server`. Expected: one recommended import for server code. Fix: say "install `idkit-server` on the backend" or drop the re-exports from the docs.
10. **`app_not_migrated` is the best error in the set.** It says what to do. The error example already carries a `code` and `detail` per entry in `results[]` (`"code": "verification_error", "detail": "On-chain proof verification failed."`), which is the right shape, but that `detail` still does not say what to change. Expected: the per-result `detail` to name the failing check (signature expired, nonce reused, wrong `rp_id`, proof expired, root too old). Fix: enumerate the possible `results[].detail` strings on the page, or add a machine-readable sub-code next to `verification_error`.
11. **Action model for v4 is not on the verify page.** The v4 uniqueness body has `action`; the session body has `session_id` and no action. Whether an action must be pre-registered in the portal (as in v3) or is free-form is not said. We chose one action string for both claims and disputes. Fix: a paragraph "Actions in World ID 4.0".
12. **Hard to test without a device.** Everything above the mock is untestable until a TestFlight build lands. Expected: a sandbox verify endpoint that accepts a documented fake payload and returns a deterministic nullifier per test user, so CI can run the both-sides test. Fix: that endpoint, or a published set of sandbox test vectors (payload + expected response).
13. **Android account matching.** "the browser and Google Play Store must use the same account" and "Wait at least 15 minutes" is good, concrete guidance. The iOS side has no equivalent for Apple Account mismatch. Fix: mirror the paragraph.
14. **Broken for us, not for World: the mailto.** A mailto for beta access has no ticket number and no way to check status. Fix: a form with an auto-reply.
15. **`allow_legacy_proofs` is a required boolean and nothing says what Selfie Check needs.** `selfieCheckLegacy()` "only returns World ID 3.0 proofs", so presumably `allow_legacy_proofs` must be `true` or the request is dead on arrival; the package README's example pairs `orbLegacy` with `allow_legacy_proofs: false`, which reads as a contradiction. Nothing in the typings says what happens when a legacy preset meets `false` (silent failure, `world_id_3_not_available`, client-side rejection). We pass `true` and will record the real behaviour **[pending sandbox]**. Fix: make the flag optional and default it from the preset, or one sentence in the `SelfieCheckLegacyPreset` JSDoc.
16. **"Preview: Selfie Check is currently in preview. Contact us if you need it enabled." lives only in a JSDoc comment** on `SelfieCheckLegacyPreset`, and `IDKitErrorCodes` has no code for "preset not enabled for this app" (`feature_unavailable` and `credential_unavailable` are the nearest). Expected: the preview notice on `idkit/credentials` next to the mailto, and a dedicated error code. Fix: both; the code lets the UI say "ask the operator" instead of "try again".
17. **`app_id` is typed as the template literal `` `app_${string}` ``**, but the value always comes from an env var (`string`), so every integration ends with a cast (`` as `app_${string}` ``). Fix: a runtime `isAppId()` guard, or a plain `string` with validation inside `IDKit.request`.
18. **Nothing says whether the widget is SSR-safe.** `IDKitRequestWidget` is controlled (`open` / `onOpenChange`) and mounts a shadow-DOM modal; `idkit-core` ships `idkit_wasm_bg.wasm` and detects `window`, so we load it with `next/dynamic({ ssr: false })` defensively. Fix: one line in the README, "Next.js: import with `ssr: false`", or make the entry point safe to evaluate on the server.
19. **`signal` semantics.** `selfieCheckLegacy({ signal })` accepts `signal?: string` but does not say whether it is hashed (`hashSignal` exists under `/hashing`) before entering the proof, or whether the backend must send the raw string or the hash to `/api/v4/verify`. We bind it to the staker's address so a proof cannot be replayed for another wallet, and we will find out which form verifies **[pending sandbox]**. Fix: state it on the preset JSDoc and on the verify page.
20. **`onError`'s `debugReport` is only populated after a global `setDebug(true)`** and the widget has no `debug` prop (section 3). Fix: a `debug` prop, or populate the report always.
21. **Headless agents have no widget, so we built an operator pre-verification list (design note).** Sigil's consuming agent opens disputes with nobody at a keyboard, and IDKit is a browser widget. Our workaround: the operator verifies once through the web, copies the nullifier into `WORLD_PREVERIFIED_NULLIFIERS` on the gateway, and the agent presents it as `{ nullifier }`; the gateway accepts a bare nullifier in sandbox mode only when listed (`packages/gateway/src/world.ts`), and the both-sides rule then applies to the agent like anyone else. It is a trust-the-operator step that World could remove: a server-side way to mint a delegated, action-scoped credential for an agent the human already verified (or a documented "bind this nullifier to this API key" flow) would let an agent prove personhood-by-proxy without our list. Fix: document a recommended pattern for non-interactive clients, or provide that delegation API.
22. **Sandbox tester approval is the bottleneck for a hackathon team.** Everything in sections 1 to 3 was done in a day; the two things still pending after that day, Sandbox tester approval and the Selfie Check (Beta) flag, are both asynchronous, show no status anywhere, and by other applicants' accounts often never arrive within a hackathon. A self-serve sandbox (instant enrolment for a portal account, or a web-only test flow with no TestFlight / Play step), or simply a documented test nullifier that `/api/v4/verify` returns for a published fake payload (item 12), would unblock the whole track: with either, every item marked [pending sandbox] above could have been closed the same day. Fix: self-serve sandbox enrolment, or published test vectors, whichever is cheaper to ship.

What worked well: the verify error `code` list is short and actionable; `signRequest` accepting a key with or without `0x` removed one class of bug; `useIDKitRequest` and `IDKitRequestWidget` take the same config, so switching between hook and widget is a one-line change; the `rp_context` object is type-checked end to end, so the gateway's shape mistake surfaced at compile time; the sandbox test matrix (Hot / Cold / Semi-cold × native / web) is exactly the checklist a team needs and we copied it into section 4 as our plan.
