# World ID (Selfie Check) integration notes — web side

Raw notes from wiring `components/HumanCheck.tsx` against `@worldcoin/idkit@4.2.3` (React) / `@worldcoin/idkit-core@4.2.4`. Everything below was taken from the installed typings (`node_modules/@worldcoin/idkit/dist/index.d.ts`, `idkit-core/dist/index.d.ts`) and the package README, not from memory. Feeds `FEEDBACK-WORLD.md`.

## What the web does

- `NEXT_PUBLIC_WORLD_MODE=mock` (today): a button labelled "Mock Selfie Check — World Sandbox access pending" yields `{ mock: true, nullifier: keccak256(connectedAddress | random id) }` and shows the nullifier. Same address → same nullifier, so the both-sides rule (gateway 409) is exercised end to end even without Sandbox access. Verified in the UI: opening a claim and disputing it from the same identity shows `409: one personhood proof cannot hold both sides of a claim`.
- `NEXT_PUBLIC_WORLD_MODE=sandbox`: `POST /world/rp-context { action }` → `rp_context` → `<IDKitRequestWidget open onOpenChange app_id action rp_context allow_legacy_proofs preset={selfieCheckLegacy({ signal: address })} environment="sandbox" onSuccess onError />`. `onSuccess` hands the full `IDKitResult` to the gateway as `worldProof`; the gateway reads `responses[0].nullifier`. Untested end to end: no `app_id` / `rp_id` / signing key yet.

## Confusing / missing / broken (typings + docs)

1. **`allow_legacy_proofs` is a required boolean and it is not obvious what to pass for Selfie Check.** `selfieCheckLegacy()` is documented as "only returns World ID 3.0 proofs", so presumably `allow_legacy_proofs` must be `true` or the request is dead on arrival. The README example uses `orbLegacy` with `allow_legacy_proofs: false`, which reads as a contradiction. Nothing in the typings says what happens when a legacy preset meets `allow_legacy_proofs: false` (silent failure? `world_id_3_not_available`? request rejected client-side?). We pass `true` and note it as `TODO(verify)`.
2. **"Preview: Selfie Check is currently in preview. Contact us if you need it enabled."** lives only in a JSDoc comment on `SelfieCheckLegacyPreset`. There is no error code for "preset not enabled for this app" in `IDKitErrorCodes` — the closest are `feature_unavailable` / `credential_unavailable`, and the docs do not say which one an un-enabled app receives. We cannot distinguish "user has no selfie credential" from "our app is not allowlisted" in `onError`.
3. **`app_id` is typed as the template literal `` `app_${string}` ``**, but the value comes from an env var (`string`), so every integration ends up with an `as \`app_${string}\`` cast. A runtime `isAppId()` guard or a plain `string` type with validation in `IDKit.request` would be friendlier.
4. **`rp_context` must be produced server-side, but the typings do not say how long it is valid.** `RpContext.expires_at` exists; the widget does not expose "expired, fetch a new one", and the error code `rp_signature_expired` is the only hint. Our UI fetches a fresh context on every click, which is safe but wasteful; the recommended lifetime should be documented.
5. **The widget is controlled (`open` / `onOpenChange`) and mounts a shadow-DOM modal**, but nothing in the README says whether it is SSR-safe. idkit-core ships WASM (`idkit_wasm_bg.wasm`) and detects `window`, so we load `IDKitRequestWidget` with `next/dynamic({ ssr: false })` defensively. A one-line "Next.js: import with ssr:false" note would save everyone this experiment.
6. **`signal` semantics for `selfieCheckLegacy({ signal })`**: we bind the proof to the connected Arc address so a proof cannot be replayed for another staker. The typings accept `signal?: string` but do not say whether it is hashed (`hashSignal` exists in `/hashing`) before going into the proof, or whether the gateway must pass the same raw string or the hash to `/api/v4/verify`. `ResponseItemV3.signal_hash` suggests the hash is what comes back.
7. **Two nullifier shapes.** `ResponseItemV3.nullifier` (legacy, what Selfie Check returns) and `ResponseItemV4.nullifier` ("RP-scoped") both exist; `ResponseItemSession.session_nullifier` is a string array. Whether the V3 nullifier is stable per (user, action) — which the both-sides rule depends on — is not stated in the typings. If it rotates, the rule degrades to per-proof.
8. **`environment: "sandbox"` on the request config vs. `environment: string` on the result.** The result's `environment` is untyped `string`; a gateway that wants to reject production proofs in sandbox mode (or vice versa) has nothing to compare against except a magic string.
9. **`onError(errorCode, debugReport?)`**: `debugReport` is only populated when `setDebug(true)` was called; the widget has no `debug` prop, so the global `setDebug` from `@worldcoin/idkit` has to be called somewhere before mount. Easy to miss.
10. **Hooks vs widget**: `useIDKitRequest` and `IDKitRequestWidget` take the same config union (`preset` xor `constraints`), which is nice, but the union makes spreading a config object from state a type error unless it is declared as `IDKitRequestHookConfig` up front (the README shows this, the typings do not explain why).
11. **No sandbox credentials while building.** `NEXT_PUBLIC_WORLD_APP_ID`, `NEXT_PUBLIC_WORLD_RP_ID`, `WORLD_RP_SIGNING_KEY` are empty pending Sandbox access; `POST /world/rp-context` returns 500 "not configured", which the UI surfaces verbatim. Everything in sandbox mode is therefore typed-against but not executed.
